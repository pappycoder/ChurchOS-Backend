# Service clock times and Essentials giving reports

The service form already sends time-only values. The API attempted `new Date("09:00")`, which produces an invalid date. Services now accept and return local 24-hour `HH:mm` strings, independent of calendar dates and browser/server time zones. Invalid values, full timestamps and impossible clock times return validation errors before a database write. Optional times may be omitted; explicit null clears a saved time. Overnight schedules are allowed.

Prisma still represents PostgreSQL TIME values internally as UTC-anchored Date objects; those objects never become the public service-time contract. Migration `20261022190000_service_clock_times` changes only `services.start_time` and `services.end_time` from timestamp-without-time-zone to TIME(3). Casting preserves their stored clock components, fractional seconds and nulls, without timezone conversion. Calendar dates previously attached to those recurring times are discarded. Event dates and individual attendance timestamps are unaffected. The web service editor, list and detail page consume HH:mm directly; the existing weekly calendar already expects HH:mm.

Essentials giving access now includes giving reports and the Reports generator's financial summary, plus financial exports. `reports:financial:read` and the reports-workspace permission follow the giving feature. Financial API paths require giving; other report API paths require Community reports. The shared export endpoint resolves the required feature from the report type, while its controller continues to check the matching report read permission. Member/attendance report blocks are filtered out on Essentials. Advanced analytics remains Network. Existing church/branch scope and staff permissions remain enforced. Public and billing plan cards share the updated Essentials giving-report wording.

Validation includes clock parsing/DTO validation, service creation/update/clear, plan-filtered financial report reads and exports, denied other report exports, backend/client catalog parity, frontend plan mappings, real local PostgreSQL migration/Prisma round trips, and production browser scenarios for report access and service time editing. The local test database alone was migrated.

Apply the migration, regenerate Prisma and deploy the backend and web as one release. No production migration, business-data write or deployment was performed.
