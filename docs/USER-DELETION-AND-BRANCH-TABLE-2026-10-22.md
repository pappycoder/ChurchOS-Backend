# User deletion and branch table layout

Users now has a separate Delete User action in each eligible row's More actions menu, on user detail pages, and as Delete Selected. Deactivate remains a reversible status action. Both actions require confirmation; bulk requests await every result, keep errors visible, and retry only failed targets. Self and platform accounts are excluded from deletion actions. All controls follow effective permissions.

`DELETE /profiles/:profileId/account` requires `profiles:delete`. The service scopes the target by church and actor branch, refuses self/Super Admin deletion, then atomically disables the profile, clears verified sessions and cancels unsent invitation mail. Only after that transaction succeeds does it delete the Supabase Auth identity and profile. Auth errors retain the inactive profile for retry; an already-missing Auth identity permits completing a previous interrupted attempt. The action is audited. Existing member, attendance, giving and historical records remain; optional visitor assignment links become null and authenticator/session rows cascade. No live user was deleted during implementation; Auth calls in tests are mocked.

The branch table's long-name flex cell previously wrapped names one letter per line at phone widths because shared expanded-column styling overrides `.truncate`. The name now uses explicit single-line ellipsis with its full value in the title, with the HQ badge underneath. Phone layouts omit the decorative avatar for readable text space. A table minimum width keeps columns aligned inside the existing horizontal scroller; the page/card remain bounded to the viewport. Existing sorting, filtering, pagination, archive and actions remain available.

Validation: 76 profile service unit tests, an isolated PostgreSQL deletion test retaining linked member/visitor records, six browser checks covering expanded/compact branch layouts at 375/768/1280px, delete confirmation/cancellation, protected self, error retry and read-only controls. Type checks, targeted lint and production web build pass. No database migration is required; deploy backend and web together. No live deletion or production deployment performed.
